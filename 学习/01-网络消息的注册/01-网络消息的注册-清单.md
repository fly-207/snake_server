## 一、消息格式与 TCP 分包

### 包头格式

网关初始化时通过参数 `header` 决定包头大小：

- `'S'` → 2 字节包头（`header_size = 2`）
- `'L'` → 4 字节包头（`header_size = 4`）

本项目使用 `'S'`，即 **2 字节大端序长度前缀**，表示后续 payload 的字节数。

### 客户端→服务端（C2GS）完整包结构

```
[ 2字节 包体长度 ][ 2字节 cmd编号 ][ N字节 Protobuf 编码的消息体 ]
```

- **包体长度**（2字节，大端）：紧跟其后内容的字节数（含 cmd 编号 2 字节 + PB 消息体）。
- **cmd 编号**（2字节，大端）：即 `netdefines.lua` 中定义的整数 ID，例如 `C2GSLoginAccount = 1001`。
- **消息体**：对应 cmd 的 Protobuf 序列化数据。

### 分包逻辑（C 层）

`service_zinc_gate.c` 的 `dispatch_message` 函数：

1. 将 TCP 数据追加到每个连接的 `databuffer` 环形缓冲区。
2. 调用 `databuffer_readheader()` 尝试读取包头，获得本包 payload 长度 `size`。
3. `size > 0` 时调用 `_forward()` 取出完整包交给业务服务，然后 `databuffer_reset()` 准备读下一包。
4. `size < 0` 表示数据不够，等待下次 socket 数据到来（即自动处理了粘包/半包）。

## 二、网关如何将包路由到正确的服务

### 路由机制：不是网关做路由，而是业务服务"抢占"连接

C 网关本身**不知道**业务逻辑，它只知道把包转发给"代理"（agent）。路由逻辑在 Lua 层完成，步骤如下：

**1. 网关启动（以 login 服务为例）**

`service/login/CGate.lua` 中，`CGate:New(iPort)` 通过 `skynet.launch` 启动 C 网关：

```lua
local iAddr = skynet.launch("zinc_gate", "S", skynet.address(MY_ADDR), iPort, extype.ZINC_CLIENT, 10000, version.XOR_KEY)
```

参数含义：`S`=小包头，watchdog=login服务地址，port=监听端口，client_tag=ZINC_CLIENT，max=10000，xor=加密key。

**2. 新连接建立**

客户端 TCP 连接创建后，C 网关向 watchdog（login服务）发送 `TEXT` 消息 `"%d open %d %s:0"`，触发 `service/login/textcmd/init.lua` 中的 `Cmds.open`：

```lua
function Cmds.open(source, handle, parm)
    -- source = 网关地址, handle = fd, parm = "fd ip:port"
    local oConnection = gateobj.NewConnection(source, handle, ip, port)
    oGate:AddConnection(oConnection)
end
```

**3. 绑定转发关系（关键步骤）**

`CGate:AddConnection(oConnection)` 中调用：

```lua
skynet.send(self.m_iAddr, "text", "forward", oConn.m_iHandle, skynet.address(MY_ADDR), skynet.address(self.m_iAddr))
skynet.send(self.m_iAddr, "text", "start", oConn.m_iHandle)
```

C 网关的 `_ctrl` 函数处理 `forward` 命令，将该 fd 的 `connection.agent`（业务服务地址）和 `connection.client`（网关自身地址）记录下来。此后该 fd 的所有上行包都会由 `_forward()` 发送给 `agent`（login服务）。

**4. 分发到具体处理函数**

login 服务注册了 `zinc_client` 协议（`lualib/base/net.lua` 的 `M.Dispatch`），收到 C 网关转发来的包后：

1. 解析包头：取出 `fd`（4字节）+ `iType`（2字节 cmd编号）+ PB数据。
2. 调用 `netproto.NetfindFunc("FindC2GSByType", iType)` → 查询 `netfind` 模块，返回 `{module, cmd_name}`，例如 `{"login", "C2GSLoginAccount"}`。
3. 调用 `netproto.ProtobufFunc("decode", cmd_name, pbData)` 解码消息体。
4. 调用 `netcmd.Invoke(module, cmd_name, fd, mData)` → `service/login/netcmd/init.lua`。

**5. netcmd 分发**

`service/login/netcmd/init.lua` 的 `Invoke`：

```lua
Cmds.login = import(service_path("netcmd.login"))
Cmds.other = import(service_path("netcmd.other"))

function Invoke(sModule, sCmd, fd, mData)
    local m = Cmds[sModule]      -- 按模块名找到 netcmd/login.lua
    local f = m[sCmd]            -- 按函数名找到 C2GSLoginAccount
    local oConnection = oGateMgr:GetConnection(fd)
    return f(oConnection, mData)  -- 调用处理函数
end
```

### 关于 C2GS_DEFINES.login 的作用

`cs_common/proto/netdefines.lua` 中 `C2GS_DEFINES.login` 定义了**module 名称到 cmd 列表的映射关系**：

```lua
C2GS_DEFINES.login = {
    C2GSLoginAccount = 1001,
    C2GSLoginRole    = 1002,
    ...
}
```

`netfind` 模块加载此文件后构建反查表：`iType → {module="login", name="C2GSLoginAccount"}`。

**结论**：所有 `C2GS_DEFINES.login` 中的 cmd，在被 login 服务处理时，`module` 字段均为 `"login"`，会被路由到 `netcmd/login.lua` 中对应的处理函数。但**路由到哪个 Skynet 服务**（login/scene/等）取决于该 fd 在建立连接时指定的 watchdog，而非 cmd 编号本身。不同业务服务（login、scene）各自启动独立的 C 网关实例，监听不同端口或通过连接切换实现服务分离。

## 三、业务服务处理后如何回包给客户端

### 发送路径

业务服务（例如 login）持有 `CConnection` 对象，调用：

```lua
oConn:Send("GS2CLoginError", {pid = 0, errcode = 1})
```

`CConnection:Send` 调用 `net.Send({gate=self.m_iGateAddr, fd=self.m_iHandle}, sMessage, mData)`，位于 `lualib/base/net.lua`。

**`net.Send` 打包流程**：

1. `PackData(sMessage, mData)`：
   - 用 `netproto.NetfindFunc("FindGS2CByName", sMessage)` 查到 cmd 编号 `iType`。
   - Protobuf 编码消息体。
   - 拼接：`[2字节 iType 大端][PB消息体]`，再用 `string.pack(">s2", ...)` 加 2 字节长度前缀。
2. `net.SendRaw(mMailBox, sData)`：
   - 在数据末尾追加 4 字节 `fd`（小端序）。
   - `skynet.send(iGateAddr, "zinc", sData)` 发送给 C 网关。

### 网关如何知道发给哪个 fd

C 网关 `_cb` 处理 `PTYPE_CLIENT`（即 `extype.ZINC` 对应的类型）消息时：

```c
// 取出消息尾部 4 字节作为 fd
const uint8_t * idbuf = msg + sz - 4;
uint32_t uid = idbuf[0] | idbuf[1] << 8 | idbuf[2] << 16 | idbuf[3] << 24;
// 在 hash 表中查找连接
int id = hashid_lookup(&g->hash, uid);
// 调用 skynet_socket_send 将前面的数据（去掉末尾4字节fd）发给客户端
skynet_socket_send(ctx, uid, (void*)msg, sz-4);
```

即：**fd 由业务服务拼接在数据尾部传给网关，网关据此找到对应 socket 连接发出**。

### 下行包结构（GS2C）

```
[ 2字节 包体长度 ][ 2字节 cmd编号 ][ N字节 PB消息体 ]
```

和上行结构一致，cmd 编号来自 `netdefines.lua` 的 `GS2C` 部分。

## 四、向多个玩家发送消息

C 网关本身**没有广播接口**，向多个玩家发送消息的方式：

### 方式一：逐个调用 playersend.Send

`lualib/base/playersend.lua` 维护了 `mPlayerMail` 表（`pid → {gate, fd}`），对每个玩家调用 `net.Send`，各自向网关发一次 `zinc` 消息：

```lua
for _, iPid in ipairs(lPids) do
    playersend.Send(iPid, "GS2CXxx", mData)
end
```

每次 `net.Send` 都单独给 C 网关发一条 Skynet 消息，网关再各自 `skynet_socket_send` 给对应 fd。

### 方式二：合包发送（MergePacket）

`net.PushMerge` / `net.SendMergePacket` / `playersend.SendMergePacketRaw` 先将多条消息打包成一个 `GS2CMergePacket` 协议，一次性发送给单个玩家，减少多条消息的发送次数（针对同一玩家的多条消息合并，而非多玩家广播）。

### 方式三：通过 player_send_proxy 代理

`service/net_recv_proxy` 作为中间代理，聚合同帧内的多条 `zinc_client` 消息，批量 `PushMerge` 给 host 服务，减少跨服务的 Skynet 消息次数。

**总结**：对于真正的"广播"（如全服公告），上层业务逻辑遍历在线玩家列表，为每个玩家单独经 `playersend` 发送，C 网关层不提供 one-to-many 的内置广播命令。
